# Final Engineering Summary

---

## 1. What was asked, and what governed the build

Build a system that turns a requirement into a reviewable engineering outcome through an
agentic execution model, with the orchestration layer as the critical differentiator:
non-linear, stateful, governed execution rather than linear task chaining.

Two principles drove every decision:

**The orchestration layer is the deliverable; the URL shortener is the system it operates
on.** So the shortener had to be genuinely production-shaped — an orchestrator that only
manages toy code proves nothing about orchestration — but effort went where the evaluation
weight is.

**Every signal the engine gates on must be measured, not asserted.** The test agent runs the
real suite under a real tracer. The impact agent parses the real AST. The docs agent diffs
the real schema against the real route table. An orchestrator whose gates consume simulated
inputs is a workflow diagram, not an engineering system.

---

## 2. Plan and rationale

### Sequence

1. **Service first.** The orchestrator needed something real to reason about. Building it
   first meant the impact, security, and documentation agents could be written against
   actual code rather than against a mock.
2. **Engine second.** Graph, context, state, gates, policy, approvals, rollback, metrics,
   audit, re-planning — each as a separate module with one responsibility.
3. **Agents third.** Every one performs real work: AST analysis, subprocess test execution
   with coverage, static security scanning, schema-vs-code diffing.
4. **Scenarios fourth.** Three workflows over the same engine, each stressing a different
   capability.
5. **Tests and docs throughout**, and end-to-end verification of everything at the end.

### Decisions that shaped the result

| Decision | Rationale | Cost accepted |
| --- | --- | --- |
| Readiness scheduler over a mutable DAG | A chain cannot express overlap, cannot revisit a completed stage, and cannot make approval structural | More engine complexity than a `for` loop over stages |
| Content-addressed context versions | Makes staleness *provable* rather than heuristic, and makes idempotent re-runs free | Every value must be JSON-serialisable |
| Governance serialised on the scheduler thread | The journal is a faithful serial history; no interleaving where correctness is hardest | No concurrent gate evaluation (irrelevant at this scale) |
| Event-sourced state | Resume, audit, and metrics all fall out of one mechanism and cannot disagree | Every transition must be an event |
| Deterministic agents | Reproducible runs; orchestration demonstrated without model variance | Agents cannot handle inputs outside their rule sets |
| Zero third-party dependencies | Runs immediately anywhere; consistent with a policy engine that escalates on new dependencies | Hand-written HTTP layer, metrics registry, YAML reader, coverage measurement |
| Disposable workspace per run | An orchestration system that edits your working tree is not one you run twice | Copy cost per run (~30 ms) |

## 4. Verified results

All three scenarios, run end to end:

| | Greenfield | Brownfield | Ambiguous |
| --- | --- | --- | --- |
| Status | SUCCEEDED | SUCCEEDED | SUCCEEDED |
| Nodes | 14 (5 injected at runtime) | 10 | 5 |
| Success rate | 100% | 100% | 100% (first-pass 40%) |
| Gates evaluated | 31 | 29 | 21 |
| Re-plans | 0 | 0 | **3** |
| Parallel gain | 1.04× | 1.05× | **1.98×** |
| Approvals | 1 granted | 1 granted | 1 granted |
| Tests executed | 238 @ 68.3% | 228 @ 68.3% | — |
| Audit chain | valid (53 events) | valid (41 events) | valid (35 events) |

Own test suites: **416 tests, all passing.**

Behaviours demonstrated rather than described:

- **Runtime graph expansion** — the planner injects 5 nodes and rewires `implement` into a
  barrier that did not exist at start.
- **Non-linear re-planning** — a parallel stakeholder review amends the requirements after
  design completes; architecture and decomposition are invalidated through their recorded
  read versions and re-execute. Converges in 3 events.
- **Real rollback** — a genuine test failure (a wrong regex) rolled the workspace back and
  stopped the release.
- **Retry with backoff and MTTR** — `--inject-fault`: 2 failures, 0.25s → 0.5s backoff,
  recovery on attempt 3, MTTR 0.82s.
- **Deferred approval and resume** — run pauses, decision recorded out of band with an
  attributed approver, run resumes and completes.
- **Auto-approval refusing to release** — the default `medium` ceiling denies a `high`-risk
  release. The demo needs an explicit `--risk-ceiling high`.

### Bugs the system's own gates caught during development

Reported because they are the evidence the gates work:

| Found by | Bug |
| --- | --- |
| Test gate | Generated tag regex accepted a 1-character tag → rollback, no release |
| Docs gate | The new brownfield route was undocumented because the docs agent trusted a stale route table |
| Change-control policy | `__future__` misclassified as a third-party dependency, escalating for approval |
| Requirements gate | Substring match flagged "many" inside "how many events are buffered" |
| Resume regression | A resumed run reported SUCCEEDED having never executed `release` |
| Metrics review | Entry-gate-blocked nodes were excluded from the success-rate denominator, letting a failed run report 100% |

Each is fixed and covered by a regression test.

## 5. Assumptions

**Stated where they were made, not buried here.**

1. **Scale.** ~10k links, ~100k clicks/day, single node. Drives SQLite, in-process rate
   limiting, and pre-aggregated analytics. All three are wrong at 100× and all three are
   behind interfaces.
2. **Deployment.** Single instance. Multi-replica breaks per-process rate limiting — the
   one assumption that is load-bearing and blocking.
3. **Trust.** API keys identify a caller; there is no per-key authorisation, quota, or
   tenancy. Anyone with a key can manage any link.
4. **Agent authorship.** Change plans are written by an engineer and reviewed before a run.
   The system executes and validates them; it does not synthesise novel code. **This is the
   most important assumption in the document.**
5. **Clarifications.** Supplied as run inputs standing in for a product owner's answers.
   Recorded as data so they are auditable rather than assumed.
6. **Approvals.** Filesystem-based, unauthenticated. Adequate for a prototype; not for a
   change-control system of record.
7. **Runtime.** Python 3.8+, stdlib only, POSIX-ish filesystem.

## 6. Limitations

Ordered by how much they would matter in production.

1. **Agents are not sandboxed.** Workspace confinement is a Python convention, not a kernel
   boundary. An agent that shells out has the orchestrator's privileges.
2. **A timed-out agent cannot be killed.** Its thread is abandoned and may still be writing
   while rollback restores the snapshot. Needs process isolation.
3. **The audit trail is tamper-evident, not tamper-proof.** Anyone who can rewrite the file
   can recompute the chain. Needs an append-only sink off the machine.
4. **Rate limiting does not survive horizontal scaling.** N replicas permit N× the rate.
5. **Ambiguity detection is lexical.** It cannot see semantic ambiguity with no vague
   vocabulary — *"links expire after 30 days"* passes without asking *from when*.
6. **Static analysis cannot see dynamic behaviour.** Reflection, dynamic imports, and
   runtime configuration are invisible. Test mapping proves reachability, not execution.
7. **No CVE scanning.** There are no dependencies today, but that is a property of this
   codebase, not a capability of the scanner.
8. **Coverage is statement-level, not branch-level**, with an `ast`-derived denominator that
   approximates `coverage.py`.
9. **Convergence depends on agent idempotence**, which the engine requires but cannot
   enforce. Violating it exhausts the re-plan budget and halts — noisy, not silently wrong.
10. **No LLM-backed agent exists.** The claim that one would be contained by the same gates
    and policies is argued from the `Agent.execute` seam, not demonstrated.

---

## 7. What I would build next

1. **Process-isolate agents.** Closes the only residual risk that can corrupt a workspace.
2. **Externalise the audit sink.** Tamper-evident → tamper-resistant.
3. **A real approval service.** Identity, non-repudiation, expiry.
4. **Shared-state rate limiting.** Unblocks horizontal scale.
5. **Resolve-and-pin at redirect time.** Closes DNS rebinding in the SSRF controls.
6. **One LLM-backed agent behind the existing gates.** The cheapest test of whether the
   containment claim actually holds.

---

## 8. The defensible claim

The orchestration layer executes an explicit dependency graph with entry and exit gates,
runs independent work concurrently and synchronises at barriers, carries versioned context
with full decision lineage, enforces human approval at high-impact points with a risk
ceiling automation cannot exceed, applies organisational policy that workflow authors cannot
waive, recovers through bounded retries / fallback / rollback / safe-stop, produces an
audit-grade tamper-evident trail, derives reliability metrics from that same trail, and
**re-plans when upstream outputs change** — verified by a run in which a parallel review
amended the requirements after design had completed and the affected stages re-executed.

Its agents are deterministic. That is a real limit on what the *agents* can do with novel
input, and it is stated plainly above. It is not a limit on what the *orchestration layer*
does, and every capability listed in the paragraph above is exercised by a passing test and
a reproducible run.
